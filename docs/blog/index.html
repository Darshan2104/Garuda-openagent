Garuda: the runtime around a coding agent

Most coding agents are a model in a loop with a shell. Garuda is about everything around that loop: where commands run, what the agent may touch, when work counts as finished, and what gets written down. This post walks through how each part works, how it compares with other tools, and where it's going next.

v1.2.0Python 3.12+MITmacOS · Linux · WSL 2~81k lines · 470 test files

The inner loop is the part every agent has. The layers around it are Garuda.

01 · The problem

Why build a runtime instead of another agent?

A model plus a shell gets surprisingly far. The trouble shows up once you rely on it: the agent says “all tests pass” when it never ran them, two runs edit the same files, a benchmark score moves and nobody can say why, or you switch from Claude to Codex and lose every safety setting you had.

Garuda's view is that these are runtime problems, not model problems. So it doesn't try to be the smartest agent. It tries to be the most dependable place for any agent to work, whether that's its own built-in loop on any LiteLLM model or an external harness like Claude Code or Codex.

Provider-agnostic

Any LiteLLM provider/model, or a subscription harness over ACP. Swapping models doesn't change your safety settings.

Evidence over claims

“Done” has to be backed by checks, and verification by your checks is recorded separately from the agent's own.

Honest boundaries

The docs say which layer actually confines code (Docker) and which are only guardrails, and the runtime warns you too.

Under the hood

All entry points (CLI, JSON-RPC server, Python SDK, web dashboard) funnel into one shared function, agents/setup.py::prepare_agent_run. It loads the agent profile, applies the mode preset, and builds the toolkit and permission engine. That one chokepoint is why a rule you set in the CLI also holds in the dashboard.

03 · Feature

Two kinds of runtime: native and external

Native is Garuda's own loop. It calls a model through LiteLLM (DeepSeek on OpenRouter by default), with retries, prompt caching, reasoning effort, concurrency limits and cost tracking. Garuda owns every tool call, so it can enforce every rule.

External runtimes are coding harnesses you already pay for (Claude Code, Codex, Cursor, OpenCode, Pi, Goose), launched through the Agent Client Protocol (ACP). Garuda starts the official CLI you're already logged into. It never reads or proxies your vendor OAuth tokens.

garuda run -t "Fix the failing test"                   # native
garuda run --runtime claude -t "Fix the failing test"  # Claude Code on your login
garuda run --runtime codex -t "…" --check "pytest -q"  # your check still verifies it
garuda runtime handoff --session latest --to codex     # move a native session over

Being upfront about it: Garuda records ACP runs and can run your --check afterwards, but it does not apply its native completion gate inside an external harness. The harness acts with its own authority.

04 · Feature

Permissions: every tool call gets screened

A profile (build, plan, explore, reviewer, or one of your own) bundles tools, rules and a system prompt. A permission mode decides what happens to each call. Pick a mode to see the same five commands judged differently:

In headless garuda run nobody can answer an “ask”, so it becomes a recorded deny. garuda chat and the dashboard show you the prompt, and you can answer from another terminal with garuda approvals answer.

How the screening works

Smart mode tokenizes the shell command (quotes, escapes, separators, continuation lines) and normalizes paths, including symlinked aliases of the workspace root. When it can't parse something confidently it asks rather than allowing. Hard refusals such as rm -rf / always win.

Subagents can't escalate. A child started with invoke_subagent must pass both its own rules and its parent's, and the stricter answer wins. Roles in flows have a permission ceiling that nothing below can raise.

Guardrail, not sandbox. Rules screen a command's arguments, not its results. grep '' . can still print a file a path rule denies, and shell indirection can get past a regex. Garuda's docs say this plainly and point to Docker when you need real confinement.

05 · Feature

Workspaces: where commands actually run

The agent never calls subprocess directly. Everything goes through one Environment protocol, so the same loop runs on your laptop, in a tmux pane, or in a container on another host. Bars show how strongly each kind confines code:

The sandbox kind uses Bubblewrap on Linux and Seatbelt on macOS. Seatbelt can stop writes and network, but it can't stop reads of host files. Garuda tests this, records it as an accepted limitation, and warns you when it applies.

Worktrees and leases: safe parallel edits

Every editing session takes a lease on the workspace, so two runs can't make overlapping changes. Pass --isolation worktree and each session gets its own Git branch (garuda/<session>). You merge it back only if your checks pass, inside Docker:

garuda run --bg --isolation worktree -t "Add retry to the HTTP client"
garuda run --bg --isolation worktree -t "Write tests for the parser"
garuda sessions merge NAME --check "pytest -q"   # merges only on green

Model calls, MCP servers, web tools and your hooks always run on the host, whichever workspace kind you choose.

06 · The core idea

When does work count as “done”?

This is what makes Garuda different. A native agent can't just say “I'm done”: it has to call task_complete, and a completion gate decides whether to accept. If the evidence is missing or a check fails, the agent gets told why and goes back to work.

First attempt has no evidence; second has a passing test.

How strict? You pick the mode

--modeWhat the gate checksExtra cost
interactive (default)Local structural checksnone
readonlySame, with permissions forced read-onlynone
evalAcceptance contract, LLM judge, discriminating and stable evidence (it re-runs your test), side-effect sweep~2 model calls per attempt
rigorouseval plus plan → execute → critique → repairmore

Self-check vs. verification

Garuda keeps two things apart that most tools blur together. Passing the gate is a self-check: the agent graded its own homework. A session is verified only by a check you trust, from --check, your garuda.yaml, or a project file you explicitly trusted. Each check leaves a receipt: who asked for it, the exact command, the code it ran against, and the result.

Anti-cheating detail: a check that modifies the code it's checking can't pass. Neither can one that depends on test infrastructure the session itself changed, for example an agent editing conftest.py to make pytest go green.

07 · Feature

Context: keeping long runs in the window

Long tasks produce huge tool outputs. Garuda's ContextManager handles three things:

Adaptive shaping

A single tool result may take up to ~25% of the remaining window, with floors so an error message is never cut down to nothing.

Output buffers

The full output is saved to a buffer and the model gets a pointer. It can read slices on demand, and buffers are published atomically, so a half-written capture can't look complete.

Condensing

Microcompaction and recent-window condensers summarize old turns, and token counts are calibrated against what the provider actually reports.

Project knowledge comes from AGENTS.md, skills (SKILL.md loaded on demand), and a committed .context/ pack of architecture, decisions and conventions. Memory works as a proposal: the agent suggests a note and you accept it with garuda memory review. Nothing is remembered silently.

Optionally, a cheaper collection model can do read-only investigation for the main model, which pays for search and reading with a smaller model while the expensive one keeps the decisions.

08 · Feature

Sessions: everything gets written down

Each run creates a session under ~/.agent/sessions/<id>/ with metadata, the conversation, and an append-only event log. Garuda also records the workspace's starting state, so it can tell the session's changes apart from edits that were already there.

What you can do with a session

garuda sessions show latest --json          # all four facts, machine-readable
garuda run --resume latest -t "Now add docs"  # continue the conversation
garuda run -t "Review the change from @fix-tests"   # attach another run's brief
garuda run --trajectory run.jsonl -t "…"     # export events for evaluation
garuda runtime support --session latest --select causes --preview  # failure evidence

A brief (@name) passes another session's task, state, changed files, checks and final answer, but never its raw transcript. Failure bundles keep bounded, sanitized causal evidence, so you can see the original failure and not only the last one.

All of this is also in the local web dashboard (garuda web): runs, approvals, a usage ledger of tokens and known cost by model and role, provider quota readings, and one-click starters. Traces can be exported through OpenTelemetry.

09 · Feature

Roles and flows: a small team of agents

Once you use more than one model, you name roles in ~/.agent/garuda.yaml. Each role is a harness plus an exact model, effort and permission ceiling. A flow runs roles in order, each as its own session, and passes only typed artifacts (plan, patch, review) between them.

garuda flow run plan-build-review -t "Add rate limiting" --check "pytest -q"
garuda flow resume FLOW_ID        # continue after the last finished step
garuda recovery enable            # auto-continue Codex flows after a quota reset

Consults

A role can ask another role one question mid-task. The answer comes from a read-only session on a snapshot of the workspace.

Fallbacks and quotas

If a harness is missing, logged out, or over its plan limit, a role can fall back to another. Quota recovery continues eligible flows hourly and never replays finished work.

10 · Feature

Tools and extension points

The built-in toolkit covers what a coding agent needs: bash, file read/write, edit and multi_edit, search, PDF and spreadsheet readers, image reading, tmux, web fetch and search (public network only), todos, subagents, and output-buffer slicing. Reads run in parallel (up to 8), and a write splits the batch so ordering stays correct.

11 · Context

How Garuda compares

Garuda overlaps with three groups: vendor coding agents (Claude Code, Codex CLI), open multi-provider agents (OpenCode, Aider, oh-my-pi), and minimal research agents (mini-swe-agent). Its own October 2026 source study of oh-my-pi and mini-swe-agent is careful to say that “stronger contract” doesn't mean a measured end-to-end win. Read the table the same way: it compares design focus, not accuracy.

Garuda's study found that oh-my-pi has richer coding interaction (language servers, semantic edits, AST codemods, debugger tools), while Garuda had stronger guarantees on acceptance checks, permission ceilings, reviewed memory and workspace ownership. mini-swe-agent is far easier to understand, and its conversation history maps directly onto its trajectory.

The interesting part is that Garuda doesn't compete with Claude Code or Codex. It wraps them. Run Codex as your coder and Claude as your planner on your own subscriptions, with Garuda handling the leases, the record and the final --check.

12 · Honest assessment

The good and the not-so-good

Where it shines

  • “Done” means something. Separating self-check from verification, with receipts, is rare and valuable for CI and benchmarks.
  • Honest about safety. It says what's a boundary and what's a guardrail, and fails closed when it isn't sure.
  • Brings your own agent. Mix API models and subscription harnesses in one flow, without handing over tokens.
  • Parallel without collisions. Leases, worktrees and merges gated on Docker checks.
  • Inspectable. Four-fact session state, event logs, trajectories, cost ledger, failure bundles.
  • Cheap by default. interactive mode adds no extra model calls. You opt into stricter gates.

Where it hurts

  • Lots of concepts. Profiles, modes, permission modes, roles, flows, leases, briefs. New users can feel lost.
  • ACP runs aren't gated. External harnesses get recorded and can be --checked, but don't go through the native gate.
  • No live token streaming in the native loop yet, so the terminal feels less alive than in vendor tools.
  • Local isolation is limited. Seatbelt can't block host reads, and real confinement needs Docker.
  • No Windows outside WSL 2, and a ~81k-line codebase to maintain.
  • Unproven quality gains. Benchmark scores are single-trial. The project says so, and avoids claiming wins it can't measure.

Who should use it? Teams running agents in CI or on benchmarks, people who switch between providers or subscriptions, and anyone who wants a trustworthy record of what an agent actually did. If you just want a fast chat-in-your-editor experience, a vendor agent is simpler, and Garuda can still wrap it later.
